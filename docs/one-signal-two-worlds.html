Field notes · graphdb · 29 August 2026

One Signal,
Two Worlds

In one day, a Go graph database produced four defects with the same shape. In each, a single observation was consistent with two different states of the world — and something collapsed them into one. Three were in code and documents. One was in me.

81,284 lines of source 133,602 lines of test 411 test files

The bugs worth writing about are not the ones where something is obviously broken. Those get found. The expensive ones are where the system reports a state that is true, and the reader draws the only conclusion that seems available — because the other conclusion never occurred to them.

What follows is a catalogue, not a sequence. Each case is named by its signal: the one observation that pointed at two incompatible worlds.

A missing file means two things

os.IsNotExist(err) pkg/storage
Observed On open, snapshot.json is not on disk.
World A

This is a new database. Nothing has been written yet. Start empty, report success.

World B

The data exists, in the other snapshot format. Starting empty discards all of it.

Cost. The loader chose World A unconditionally. The deployment guide told operators to roll back with GRAPHDB_STORAGE_MODE=json, which walked them straight into World B: an empty database, reported as a clean start.

The asymmetry is the tell. Opening in mmap mode does check for the other format and falls back, so a legacy database migrates upward correctly. The JSON path never looked. One direction distinguished the two worlds; the other did not.

A test that agreed with itself

id1 == id2 crash-recovery test
Observed Both assertions pass. The node written before the snapshot and the node written after it are each found by vector search.
World A

The index rebuild ran over the final post-replay node set. This is exactly what the test claims to prove.

World B

There is only one node. Both assertions matched it, because both IDs are 1 and k=1 returns it either way.

Cost. World B, for nearly two months. The test's middle session was built from a bare config, so it opened the store on the JSON path — case 1, from the inside. It got an empty database, nextNodeID restarted, and the second node was handed the first node's ID.

This test was not neglected. It was written deliberately, with a comment explaining the subtle thing it existed to catch. It became wrong later, on the day an unrelated default changed, and nothing announced that. A passing test is the one artefact nobody re-reads.

Adding a guard to production code turned out to be the cheapest way to audit a test nobody had watched fail.

A build failure that was not the build's

go build ./... → 7 errors my terminal
Observed The project's most basic command fails, in a directory that is unquestionably the project.
World A

The repository is broken. Anyone who clones it hits this immediately. Fix it before showing anyone.

World B

The repository is fine. My working tree holds a gitignored directory that no checkout contains.

Cost. I picked World A, and recommended fixing it as the single most important task before publishing the project. It was World B. The repair would have changed nothing a visitor sees, and could not have been committed at all — the path is in .gitignore.

Worse, the project's own guide for contributors asserted World A in writing — so the false claim was not merely available, it was documented. A wrong note in an orientation file costs every future reader the same mistake, which is a strictly worse failure mode than a wrong line of code: code gets tested.

A number that was a subset

"nine" a handoff summary
Observed A session summary opens: "Nine defects were found, and five of them were in the instruments rather than in the system."
World A

Nine is the total, five is a subset of it, and the ratio is the headline: more than half the defects were in the tests.

World B

Thirteen is the total. Nine is the coupling subset. Five counts a different population entirely — hollow tests, not defects.

Cost. I quoted "13 defects, 5 in the instruments" three times in one day — a figure belonging to neither world — and proposed it as the headline of this essay. The source that settles it was four rows further down the same file: "9 of 13 defects were coupling defects."

The real taxonomy is more interesting than the ratio I nearly published. Of the thirteen: nine were coupling defects, at the seams between components; one was inside a single component; three were in process or in the contract of a test. Separately, five existing tests were found to be decoration.

Note where the error lived. Every claim below that summary cited a pull request. The summary cited nothing — and it is the line everyone quotes, because it is the line written to be trusted.

What actually separates the worlds

None of these were fixed by looking harder. Each needed a second, independent observation that the two worlds disagree about — which is a design task, not a diligence one.

  • Refuse, don't guess When one condition carries two meanings and you cannot tell which, the correct behaviour is an error, not a default. The loader now refuses a JSON-mode open when the other snapshot is present, and names the file.
  • Positive control "No output" and "the instrument is broken" look identical. Before believing a negative, make the check report the opposite on purpose. A deliberately broken file proved the clean build could still fail.
  • Name the artefact A result is about the thing that was actually read — a worktree, an archive, a tag, a suppression list. Put the artefact in the verdict, because a pass on the wrong one is indistinguishable from a pass.
  • Watch it fail Every fix lands with a test seen failing against the pre-fix code, and the pull request records what it printed. A test that has never been red is an assertion about the world, not evidence of it.
  • Pin the collision The repaired crash-recovery test now asserts id1 != id2. It cannot pass on a single node again — the shortcut that faked the result is now itself a failure.

Why this beats a defect count

It is tempting to report a tally — we found N bugs, M of them in the tests — and case four is what that instinct earns. A count compresses away the only part that transfers.

What transfers is the shape. Ask of any check: is there a second world in which this same output is fine, or in which it is catastrophic? If yes, the check is not yet an instrument. That question found a silent data-loss path, a test that had been lying for two months, a build failure that did not exist, and a number I was about to publish.

Three of those four were caught by machinery built for the purpose. The fourth was caught by reading four rows further down.

graphdb is an open-source graph database written from scratch in Go — LSM-tree storage, a write-ahead log, an mmap-backed snapshot format with lazy reopen, and multi-tenant isolation. The testing machinery referenced here — mutation testing, coupling coverage, per-package coverage floors measured on CI, invariant checkers, fault injection, and a self-test on every gate — is in the repository, as are all four defects above and the pull requests that closed them.
